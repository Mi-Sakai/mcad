# DESIGN.md への追記書式

DESIGN.md は大きい。**新規に書き起こさず、既存の書式に倣って追記する**
のが原則。以下は実際の記述から採った型。迷ったら該当箇所を `grep -n` で引いて
現物に合わせること。

## 文書の構造

```
## 1. 概要 / 2. 技術スタック / 3. アーキテクチャ / 4. 主要な設計判断の理由
## 5. タスク分割(実装フェーズ用)      … M1〜M3 と MVP 検収基準
## 6. M4: 入出力の一貫性(v0.4.0)
## 7. 長期ロードマップ(M5〜)          … 追記の大半はここ
     ### マイルストーン一覧 / 将来の検討項目 / v1.0.0 の定義
     ### M5〜M12 の各マイルストーン設計章
```

M4 以降の各マイルストーンは
`### <名称>(v<バージョン>)の設計(<日付> 策定、実装<状態>)`
という統一見出しで、内部は **設計判断 → タスク分割 → 検収基準** の順。

## 1. 設計判断

見出しは `#### 設計判断`(マイルストーン内)または `### 設計判断`。
番号付きで、タイトルを太字にしてコロンで区切る。

```markdown
#### 設計判断

1. **変換はShapeのメソッドとして mcad-geom に置く**: `translated` に加えて
   `rotated(pivot, angle)` / `mirrored(axis_a, axis_b)` を追加する(`translated` に
   合わせた過去分詞・非破壊命名。2026-07-19 実装済み、タスク17)。app 層での座標
   いじりを禁止し、`Command::ModifyEntity` / `AddEntity` 経由を維持する
```

- タイトルは短い断定形の名詞句(「〜は〜へ置く」「〜は〜しない」)
- **理由を必ず本文に書く。** 「こうする」だけで終わらせない
- 確定日・実装日・タスク番号を括弧で添える(`2026-07-19 実装済み、タスク17`)
- 見送った案は「スコープ外」と明記して残す(後から蒸し返さないため)

## 2. 実装時追記

設計を確定したあと、実装中に決まったことを**元の設計判断を書き換えずに**足す。
親の設計記述の中、判断番号の直後に置く。

```markdown
- **実装時の設計方針追記(2026-08-12、ユーザー承認)**: 出力色モードは**図面の属性
  ではなく、エクスポート設定+`config.json`の既定値**として持つ(印刷色は表現の選択
  であり図面内容ではないため、`SheetMeta`には入れない)。
```

- 見出しは `- **実装時の設計方針追記(<日付>、<承認者>)**:`
- **日付は必須。** 承認を経たなら「ユーザー承認」と書く
- 既存の記述を改訂する場合は
  `- **(d) 判断7 記述の改訂**:` のように、どの判断のどこを直すかを明示する
- **履歴は書き換えない。** 古い判断は残し、上に追記を重ねる

## 3. 検収基準

マイルストーン単位なら `### 検収基準(M4完了の定義)`、
機能単位なら `- **検収基準**:` で項目化する。

```markdown
### 検収基準(M4完了の定義)

- GUIからDXFを開き・書き出しでき、importのスキップ件数がステータスに表示される
- 保存→1操作→undoで保存時内容へ戻ると、タイトルの`*`が消え未保存確認も出ない
- 全段で fmt / clippy / workspace test が通り、GUI変更(12・13)は手動スモークテストを記録する
```

機能単位で条件が複雑な場合は `(i) (ii) (iii)` を使う:

```markdown
- **検収基準**: (i) 既定(新規/旧 config とも)で SVG/PDF の全作図線・寸法・文字・枠が
  黒、背景が白。(ii) 青図モードで同要素がすべて白、背景がプルシアンブルー。(iii) 「元の
  色」モードの SVG 出力が改修前実装とバイト一致。(iv) モードは画面描画・`.mcad`・DXF へ
  無影響。(v) fmt / clippy / workspace test 通過、手動スモークテスト記録。
```

**必ず入れる2点**:

- 「fmt / clippy / workspace test 通過」— 例外なく全検収基準に入っている
- GUI変更を含むなら「手動スモークテストを記録する」

**書き方のコツ**: 検収基準は「実装したか」ではなく**「実機で何を確認すれば
合格と言えるか」**を書く。そのまま手動スモークテストのチェックリストに変換できる
粒度にする。

## 4. 達成・スモークテストの記録

検収基準の**直後**に、達成できたことを太字1行で足す。

```markdown
**→ 全項目 v0.4.0 で達成済み(2026-07-16、手動スモークテスト7項目をLinux環境で確認)。**
```

```markdown
**→ 全項目 v0.8.0 で達成済み(2026-08-11、タスク35a〜44完了)。手動スモークテスト実施済み:
タスク36(線幅・線種の画面反映)・37(注記の紙基準表示)・42(両極端の座標スケールでの
手動ズームフィット)のすべてで問題なし。**
```

- `**→ ` で始めて `**` で閉じる
- 日付は `YYYY-MM-DD`
- 実施者は「ユーザー」と明記する
- 項目数を数字で書く(`全項目` / `全7項目` / `全10項目`)
- Codex レビューの指摘に対応した場合はその旨も同じブロックに残す

## 5. 随時対応(マイルストーン外)

ロードマップに載せないが忘れたくない項目。7章に置く。

```markdown
- **随時対応(マイルストーン外)**: M4 レビューの任意指摘2点 — DXF import ステータス
  文言の正確化、`FIT_MIN_MARGIN` の画面ピクセル基準化(単位系確立後)。いずれも次に
  該当箇所を触るタスクに相乗りさせる。
```

- `- **<種別>(<括弧内の位置づけ>)**: <内容>` の形
- 種別の例: 「随時対応(マイルストーン外)」「実験トラック(番号外・任意)」
- **いつ着手するかのトリガーを必ず書く**(「次に該当箇所を触るタスクに相乗り」
  「単位系を確定させるタイミングで」など)
- 指摘の出どころを添える(`Codex M7 レビュー(2026-07-26)指摘`)

## 追記するときの禁止事項

- **既存の記述を消さない。** 誤りでも取り消し線ではなく、改訂の追記で上書きする
- **要約しない。** 既存の粒度(ファイルパス・関数名・定数名まで書く)に合わせる
- **日付を省かない。** 後から経緯を追えなくなる
- 行番号での参照は書かない(追記のたびにズレる)。見出し名か judgement 番号で指す
