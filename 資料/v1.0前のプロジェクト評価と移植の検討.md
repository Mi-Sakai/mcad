## 2. 出来栄えの評価

### 強いところ: 壊れにくさ
次の規律が M1 から M13 まで崩れずに守られている。拘束ソルバーのような難しい機能を後から足しても土台が崩れなかったのは、この規律の成果と見る。

- 文書の変更は必ず `Document::apply(Command)` を通す。`Batch` は失敗したら全体を元に戻す
- 削除した図形・レイヤーは墓標として残し、undo/redo をまたいでも ID が変わらない
- クレートの依存は app → io → core → geom の一方向だけ
- 毎回の変更で fmt / clippy / test・Codex のレビュー・手動スモークテストを通し、`DESIGN.md` に記録する

個人用の CAD として v1.0 を名乗れる品質と評価する。

### 弱いところ
1. **UI が `main.rs` に集中している**: 18,563 行。タブ型ドキュメント UI の検討(`DESIGN.md` 7章)でも、状態の直接参照が約100か所あり、切り分けは main.rs 全域に及ぶと見積もっている。
2. **画面と PDF で文字のフォントが違う**: 画面の英字は egui 既定の Ubuntu-Light、SVG/PDF は同梱の Noto Sans JP。画面では文字の描画枠の下端をベースラインとみなす近似もある。実使用3枚目の `M12` の重なりも、この「文字の幅をどこで決めるか」の延長で起きた。
3. **見つけやすさと統一感**: コマンドを画面上で探す手段(メニューバー・リボン)が無い。UI の日本語化は領域ごとに進めている途中。
4. **DXF の往復が非対称な経路がある**: 寸法・表は書き出すときに分解し、読み戻すと元の種類に戻らない(`dxf` クレート 0.6.1 の制約による。AGENTS.md)。

## 3. 上流工程の評価: 「構造は強く、要求は遅かった」

ユーザーの「紆余曲折して寄り道も多かったのでは」という感覚は当たっていると見る。ただ原因は設計の弱さではなく、**要求を確かめる時期**にあった。

- **構造の上流は強かった**: M1〜M4 で決めた土台(クレートの分割・Command・墓標・f64 のワールド座標)は M13 まで一度も作り直していない。
- **要求の上流は遅かった**: 「何を描くための CAD か」を実際の図面で確かめたのは v0.13.0 の後だった。`DESIGN.md` 7章「マイルストーン構成の位置づけ」は、M6〜M8 の分け方を「一般的な CAD 機能の類推による仮説であり、実使用データがない」と自ら書いている。
- **その結果として起きたこと**:
  - 拘束ソルバー(M13)は、v1.0.0 の要件に含めないと定義しながら(7章「v1.0.0 の定義」)、実使用より先に作った
  - 実使用ですぐ出た要望(文字の座標打ち・文字の中央揃え・φ/R の表示)は、どれも小さく基本的なものだった
  - 範囲の拡大(M8 に単位・用紙・表題欄を追加)、マイルストーンの差し込み(M12)、部品欄の列の作り直し(v0.11.1。Codex のレビューは6回目で承認)などの手戻りがあった
- **ただし、寄り道の一部は意図したもの**: mcad は tcad(`~/tcad`)の土台という役割もあり、拘束ソルバーや geom 層の充実はそちらにも効く。
- **総合**: 最初の1か月で実際の図面を3枚描いていれば、同じ品質にもっと短い期間で着けたと見る。

**次の案件への教訓**: 土台を固めたら、早い段階で実際の題材を1枚描き、その痛点からマイルストーンを組む。今回の実使用の手順(題材 → 手順書 → ユーザーが描く → メモ → 分類)は、それ自体が良い型になった。

## 4. DESIGN.md を清書して渡せば、同品質で作れるか

### 結論(評価)
「読んで、この言語で作って」の一言では、Fable 5.2 でも Opus 5.5 でも同品質にはならない。理由は次の3つ。

1. **品質の多くは、文書ではなくテストとコードにある**: 1,867 個のテストには、Codex のレビューやスモークテストで見つけた細かい場合分けが入っている。`DESIGN.md` が書いているのは「判断と理由」で、仕様のすべてではない。しかも経緯の記録として書いてあり(追記・改訂を重ねた形)、そのまま仕様書として読める形になっていない。
2. **ライブラリに固有の知識は、言語を変えると使えない**: `dxf` クレートの地雷(`dxf-constraints` skill)、egui の文字の置き方、`rfd` のブロッキング呼び出し、フォントの実測値の持ち方は、Rust とそのライブラリに固有。別の言語では、別の制約を一から踏み直すことになる。
3. **GUI の手触りは人が触って確かめるしかない**: たとえば記号欄で「φ(既定)」と「φ」が2回並ぶ件は、テストでは見つからず、スモークテストで初めてわかった(2026-11-08)。モデルが自分だけでは検収できない部分。

### Fable 5.2 と Opus 5.5 の違い
- **確認した事実**: Fable 5.2 は 2026-11-09 公開の最新の上位モデル(Mythos 5.2 と同時。API の ID は `claude-fable-5-2`)。出力は Fable 5.1 より最大30%速いと発表されている。料金は報道によって数字が食い違い、確認できていない。両モデルをこの課題で比べた実測は無い。
- **評価(推測)**:
  - Fable 5.2 は、1回の指示で長く整合を保つ力が上。クレートをまたぐ実装を、途中で崩さず遠くまで進められる。
  - Opus 5.5 は、マイルストーンに分けて、レビューで差し戻しながら進めるのに向く。
  - どちらも上の3つの壁は越えられない。差が出るのは「手戻りの少なさ」で、「一言で同品質」は可能にならない。
- **費用の考え方**: この環境の方針(`~/.claude/CLAUDE.md`)では、Fable は「分けると整合が取れない長い実装」に限って `implement-fable` へ委譲する。移植でも、文書モデルと保存形式の一体実装のような区間に絞るのが見合う。

## 5. 他言語への移植を検討するときの材料

### そのまま持っていけるもの(言語に依存しない)
- **アーキテクチャの不変条件**: AGENTS.md「アーキテクチャ不変条件」の全項目(一方向の依存・Command 経由の変更・墓標・Batch の原子性・読込は Command で再構築して履歴を消す)
- **設計判断とその理由**: `DESIGN.md` と `docs/design/M5〜M13.md` の設計判断。特に寸法の GPS モデル(M9)、表・部品表(M10)、拘束ソルバー(M13)
- **`.mcad` 形式**: JSON で版番号つき(v1〜v9)。移植版が同じ形式を読み書きできれば、図面を共有できる。fixture は `crates/mcad-io/tests/fixtures/`
- **フォントの実測値**: 同梱の Noto Sans JP から測った英字の送り幅・大文字の高さ(`mcad-geom` の `symbol.rs`)。同じフォントを使う限り、そのまま使える
- **検収基準とスモークテストの記録**: 各マイルストーンの「検収基準」は、そのまま移植版の受け入れ項目になる
- **実使用の題材**: 手順書3つ(リポジトリ直下、追跡外)と、ユーザーの図面・PDF・メモ(`~/ドキュメント/mcad/`)。移植版の検収に使える

### 移植先で作り直しになるもの(Rust とライブラリに固有)
| 領域 | 現在の実装 | 移植で起きること |
|---|---|---|
| GUI | egui / eframe 0.35(即時モード) | 状態の持ち方・文字の置き方・入力処理を作り直す。`main.rs` の集中も、ここで分割し直す機会になる |
| DXF | `dxf` クレート 0.6.1 | 制約(R2007 固定・ACI 色のみ・TEXT の位置基準など)はクレート固有。移植先のライブラリで実測し直す |
| PDF / 文字の輪郭 | pdf-writer・ttf-parser | 文字は輪郭に変換して出しているので、同じ方式を取れるライブラリが要る |
| ファイルダイアログ | rfd(同期呼び出し) | プラットフォームごとの癖を確かめ直す |
| ID の安定 | slotmap(`Option<T>` の墓標) | 概念は持っていけるが、データ構造は移植先で選び直す |

### 移植の前にやっておくとよいこと
1. **`DESIGN.md` を仕様書の形に清書する**: 経緯(追記・改訂の重なり)を残したまま、「現在の仕様」と「検収基準」だけを抜き出した版を別に作る。
2. **テストの意図を受け入れテストの一覧にする**: 1,867 個のテストを、言語に依存しない「入力 → 期待結果」の一覧(特に `.mcad`・DXF・SVG の往復とスナップショット)へ落とす。
3. **進め方**: マイルストーンごとに人がスモークテストする進め方を変えない。

## 6. v1.0.0 の後に議論を再開するときの論点

1. **移植の目的**: 何のために別の言語にするのかを先に決める(配布先・性能・他の製品への組み込み・学習など)。目的によって、移植するか、`main.rs` の分割などのリファクタリングで足りるかが変わる。
2. **tcad との関係**: tcad は `mcad-geom` / `mcad-core` を path 依存で使っている。移植するなら、tcad をどちらに載せるかを決める。
3. **範囲**: 全機能か、geom/core だけか、`.mcad` を読み書きするビューアだけか。
4. **モデルの使い分け**: 第4節のとおり。清書と受け入れテストの一覧を先に作ってから、どこを Fable に任せるかを決める。
5. **v1.0.0 後の課題との順番**: M14(文字の揃え、設計済み・見送り)、メニューバー・リボン、実使用で出た4件(切断線・フィレットへの寸法・寸法線の整列・矢先のグリップ)、タブ型ドキュメント UI。移植の前に入れるか、移植版で入れるか。
